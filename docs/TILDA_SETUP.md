# Заявки из Тильды

Источник: https://sixteen-detailed-flag.tilda.ws/ (проект 54664903).
Пользователь подтвердил передачу реальных заявок в текущую Neon в США.
Это подтверждение размещения, а не юридическое заключение о соответствии требованиям.

## Подключение

1. Опубликовать обработчик `POST /api/integrations/tilda` на Vercel.
2. Применить добавочную миграцию `db/002_tilda.sql` к той же базе, что использует Vercel. Она создаёт только таблицу идентификаторов доставок; существующие записи CRM не меняет. Общая команда `npm run db:migrate` также применяет её.
3. Добавить в Vercel Production переменные из секции Tilda в `.env.example`. Создать случайный секрет не менее 32 символов. Не использовать секрет в URL или публичных скрытых полях формы. Перезапустить развёртывание после настройки окружения.
4. Тильда → Настройки сайта → Формы → Webhook:
   - URL: `https://bda-lawyer-crm.vercel.app/api/integrations/tilda`
   - API METHOD: `HEADER`
   - API NAME: `X-BDA-Tilda-Key`
   - API KEY: значение `TILDA_WEBHOOK_SECRET` (вводить самостоятельно, не присылать в чат).
   - Cookies выключены. Отправка только после оплаты выключена.
5. Подключить новый получатель к формам, сохранив прежних получателей. Перепубликовать затронутые страницы.
6. Проверить вымышленную заявку и повторную доставку. Отправка через живую форму также уведомляет её прежних получателей; предварительно согласовать тестовое уведомление.

До этих действий изменение кода само по себе не подключает сайт.

## Поведение

- Имя и телефон: `Name`/`Phone` или `Имя`/`Телефон`. Телефон должен содержать 11 цифр по текущему правилу CRM.
- Источник «Сайт», этап «Новые лиды», ответственный `TILDA_OWNER_ID` (изначально u2). Требуется активный аккаунт менеджера. Следующий шаг — связаться с клиентом в текущую дату Asia/Almaty.
- Направление, случай, описание, email, отметка согласия и ссылки на файлы остаются в описании лида. Совпадающее название услуги используется напрямую; иначе применяется `TILDA_DEFAULT_SERVICE` до квалификации менеджером.
- Файлы не скачиваются и не копируются в CRM. Cookies и неизвестные поля не сохраняются. Секрет и персональные данные не выводятся в журналы обработчика.
- Принимаются только перечисленные в `TILDA_FORM_IDS` формы. Новые формы нужно явно добавить. Права, сумма и этап из входящего запроса игнорируются.
- `tranid` предотвращает повторное создание при повторной доставке. Новый запрос с тем же телефоном, но другим `tranid` — отдельный лид. Клиенты и дела не создаются автоматически.
- Изменение CRM и квитанция доставки сохраняются в одной транзакции под той же блокировкой, что и действия сотрудников. История указывает автора «Тильда».

## Контроль и отключение

`200 ok` означает сохранение (или ранее сохранённую доставку); проверочный `test=test` не создаёт лид.
`401`: неверный ключ; `422`: неизвестная форма/некорректные поля; `503`: окружение, менеджер, миграция или база недоступны.
Содержимое ошибки не включает заявку. Проверять ошибки доставки в разделе заявок Тильды.

Тильда ожидает ответ за 5 секунд и повторяет неудачную доставку дважды с интервалом в минуту. Холодный запуск базы или блокировка могут задержать ответ; квитанция защищает от дубля при повторе. Реальную задержку необходимо проверить после развёртывания.

Для остановки снять нового получателя с форм и перепубликовать их, либо убрать `TILDA_WEBHOOK_SECRET` и повторно развернуть CRM. Не удалять квитанции и лиды при откате. Добавочная таблица совместима со старой версией приложения.

Документация: https://help.tilda.cc/forms/webhook
